3. **指示書外の設計判断が必要になった場合、または解決できない問題に直面した場合は、勝手に進めず停止してメインループへ報告する**
4. **実 API を叩かない**(SDK はモックする)。API キーやシークレットを print・ログ出力しない。ユーザーデータ(`~/Library/Application Support/newsvideo`)は読み取りのみ可。ネイティブレンダラーの計測は、ユーザーデータをスクラッチパッドにコピーして行ってよい

6. ロジック実装・レビュー・テストは Codex(codex プラグイン)に委譲してよい
7. 完了条件: `npm run typecheck` / `npm run lint` / `npm test` / `npm run audit:licenses` がすべて通ること。ネイティブレンダラーを変更した場合は `npm run test:native` も通すこと
8. 完了報告に含めるもの: 変更ファイル一覧、主要な設計判断とその理由、**改善前後の時間の見込み(計測できたものは実測)**、テスト結果、未解決事項、統合時に実 API で確認すべき項目、worktree のパスとブランチ名、reset 後の HEAD

## 1. ユーザー決定事項(2026-09-26)

- 動画の fps は **30fps** を既定にする
- 自動生成は全自動を既定にする(M1 で実装済み)

メインループ判断:
- プロバイダごとの同時実行数の既定: テキスト 4 / 画像 2〜3 / TTS 4。OpenAI の画像は 1 分あたりの枚数も制御する(Tier1 は 5 枚/分)
- 並列中に 1 件失敗したら、新しい処理は始めず、実行中のものは完了させて成功分を保存する
- 素材ができたパートから動画を先に作る構造的な改修(提案書の D2)は今回は行わない

## 2. 進捗データの契約(M4 と共有)

- `shared/project/jobs.ts` の `job.progress`(メインループが追加済み)を、ジョブエンジンが実行中に更新する。形は次のとおり。変える必要が出たら停止して報告する(M4 の画面がこの形を読む)
  - `script` / `prompt` / `image` / `audio`: それぞれ `{ done, total }`。並列に進む工程も同時に表せる
  - `video`: `{ percent, message? }`
- 更新のたびに既存の `job:statusChange` イベントが画面に届くことを確認する。更新が高頻度になる場合(動画の percent など)は、保存と通知の回数を間引く(例: 1 秒に 1 回、または 5% 刻み)

## 3. 実装範囲

### 3.1 ジョブの並列化(`electron/jobs/engine.ts`)
提案書の調査で、画像工程と音声工程がパートごとの `for` ループで 1 件ずつ処理されていることが分かっている。3 パートの実例の正味時間は、台本 7 秒 / 画像プロンプト 60 秒 / 画像 104 秒 / 音声 26 秒 / 動画 148 秒。
1. 台本ができたら、全パートの画像プロンプト生成と音声生成を始める。画像プロンプトができたパートから画像生成に進める。同時実行数はプロバイダごとの枠で制御する
2. Claude のプロンプトキャッシュを効かせるため、同じ記事への画像プロンプト生成は、1 本目の応答が始まってから残りを送る(M3 がコードコメントに方針を残している)
3. 並列化の前提となる変更(提案書の B1〜B3):
   - 実行中の処理の記録(`pendingOperation`)を、複数件を持てる形にする。再起動時に未確定費用を数える処理も対応させる。旧データ(単一の `pendingOperation`)も読めるようにする
   - 予算は、実行中の処理の見込み額を予約してから判定する。予算停止の保存が並列時のリビジョン競合で失敗しないようにする
   - キャンセルや失敗のときは新しい処理を始めず、実行中のものは完了させて保存する
4. 並列にしても、パート単位の変更検知(fingerprint)と保存の直列キューで整合性が保たれることをテストで確認する

### 3.2 同時実行とレート制御(`electron/utils/generationPolicy.ts`、`electron/ipc/image.ts`)
- 同時実行の枠を、テキストと画像で分ける(現状はどちらも `'openai'` の枠を共有している)
- 既定の同時実行数は §1 のメインループ判断に合わせる。既存の設定 `generationConcurrency` との関係を整理し、設定画面に出す項目が変わる場合は M4 のために報告に書く
- OpenAI の画像生成に、1 分あたりの枚数の制御を入れる。429 のときは `retry-after` に従う

### 3.3 動画の書き出し
- fps の既定を 30 にする(出力設定の既定値)。既存プロジェクトの保存済みの出力設定は変えない
- 調査では、ネイティブ経路で `videoBitrate`(8M)と `audioBitrate`(192k)が反映されていなかった(実出力は 12〜15Mbps、24kHz モノラル 32kbps)。反映させるか、反映できない理由を報告する
- 進捗: ネイティブレンダラーの進捗を、画像 1 枚ごとの最初と最後だけでなく、一定フレームごとに出す。JS 側で解釈し、連結にも進捗を付ける。ジョブの `job.progress.video` と、手動の書き出しの既存の進捗イベントの両方に流す
- 停止: ジョブの停止で、書き出し中のネイティブプロセスも止める。書き出し処理を、プロジェクトや依頼元ごとに管理する(今は全体で 1 つの変数)
- ウォッチドッグ: 進捗が一定時間止まったらプロセスを止めて、分かりやすいエラーにする
- 60fps を維持するための改修(提案書の D1)は不要。ただし 30fps でも連結の再エンコードを省けるなら省く
